# cuda-bindings

Generated raw Rust FFI bindings to the CUDA toolkit libraries used by this workspace.

Use `cuda-core` for wrappers around these raw bindings.

# Notes

- The bindings are generated by `cargo xtask bindings` and **committed** under
  `generated/<target>/` (`types.rs`, `cuda_driver_api.rs`, `cuda_driver_shims.rs`,
  `curand_api.rs`, `curand_shims.rs`), with `generated/meta.json` recording, per
  target, the toolkit `CUDA_VERSION`, the SHA-256 of `cuda.h` / `curand.h` and the
  header cfgs (`cu_mem_location_anon_union`, `cuda_has_cuEventElapsedTime_v2`,
  `cuda_has_cuLaunchHostFunc_v2`, `cuda_has_multicast`). Building needs **no CUDA
  toolkit and no libclang**; `libcuda` / `libcurand` are loaded at run time per symbol
  (a symbol missing from the installed driver returns `NOT_FOUND`), so bindings from
  the newest toolkit serve every driver >= 13.0.
- `build.rs` selects `generated/<target>/` from `CARGO_CFG_TARGET_{OS,ARCH,ENV}`,
  replays the recorded cfgs (also exported to dependents as `DEP_CUDA_BINDINGS_<CFG>`
  through the `links` key; `cuda-core` gates `cuda_has_multicast` on it) and fails for
  an unsupported target. If a toolkit is discoverable and newer than the recorded
  version it only prints a `cargo:warning` to regenerate.
- Why committed: consumers (and CI) build without a CUDA toolkit or libclang, like
  `cudarc`, and every machine compiles identical bindings. Why `build.rs` only warns
  about a newer toolkit: switching bindings silently would make the build depend on
  what happens to be installed.
- Supported targets (table in `shared.rs`, one directory each because C enum widths and
  layouts differ per platform): `x86_64-pc-windows-msvc`, `x86_64-unknown-linux-gnu`,
  `aarch64-unknown-linux-gnu`.

# Regenerating

```
cargo xtask bindings [--toolkit DIR] [--target KEY]... [--clang-arg ARG]... [--out DIR]
```

The default target is the host. The toolkit is `--toolkit`, else the first set variable
of `CUDA_TOOLKIT_PATH` / `CUDA_HOME`, else the standard install locations (CUDA 13.0+).
The `targets/<dir>/include` layouts (Jetson/Tegra, sbsa, redistributables) are probed
for `cuda.h`; `CUDA_TOOLKIT_TARGET_DIR` names one `targets/` directory by hand, like
nvcc's `-target-dir`. Other targets' entries in `meta.json` are kept, so each platform
can be regenerated where its libc headers exist. Commit `generated/` as is (it is
marked `-text -diff` in `.gitattributes`: the files are byte-exact, and the test
compares bytes).

Cross generation needs the target's libc headers for clang. The checked-in sets were
produced as follows:

- `x86_64-pc-windows-msvc`: on Windows, `cargo xtask bindings` (libclang + MSVC headers).
- `x86_64-unknown-linux-gnu`: inside WSL Ubuntu with `/usr/local/cuda`, `cargo xtask bindings`.
- `aarch64-unknown-linux-gnu`: in WSL with the cross libc headers
  (`apt-get download libc6-dev-arm64-cross linux-libc-dev-arm64-cross`, `dpkg -x` into a
  directory `ROOT`) and the x86_64 toolkit's headers (the driver headers are
  architecture independent):
  `cargo xtask bindings --target aarch64-unknown-linux-gnu --clang-arg -nostdlibinc --clang-arg -isystem --clang-arg ROOT/usr/aarch64-linux-gnu/include`

Why a test: `build.rs` never regenerates, so a stale or hand-edited tree would go
unnoticed otherwise. `cargo test -p xtask` regenerates the host target into a temp directory and requires
byte equality with the committed files (skips with a printed reason when no toolkit or
libclang is available; `CUDA_BINDINGS_REQUIRE_TOOLKIT=1` makes the skip a failure).
